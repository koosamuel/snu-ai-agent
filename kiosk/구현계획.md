### 팀 공동 작업 절차

팀원은 저장소 Collaborator 권한을 받은 뒤 아래 순서로 작업한다.

```bash
git switch main
git pull --rebase origin main

# kiosk/ 안의 파일 수정
git add kiosk
git commit -m "변경 내용 요약"

# 다른 팀원의 최신 변경을 반영한 뒤 업로드
git pull --rebase origin main
git push origin main
```

- 작업을 시작할 때와 push 직전에 반드시 원격 `main`의 최신 변경을 반영한다.
- 커밋 범위는 자신이 수정한 `kiosk/` 파일로 제한하고, 다른 팀원의 파일을 임의로 되돌리지 않는다.
- 같은 파일을 동시에 수정하지 않도록 작업 시작 전에 담당 파일과 작업 내용을 팀 채널에 공유한다.
- rebase 중 충돌이 발생하면 내용을 확인해 해결하고 테스트한 뒤 push한다. 해결이 불확실하면 강제 push하지 않고 팀원과 함께 확인한다.
- `git push --force`와 `git push --force-with-lease`는 `main`에서 사용하지 않는다.
- 변경 후 `npm --prefix kiosk test`와 `npm --prefix kiosk run check`를 실행하고 통과한 상태만 push한다.

## 2. 기본 구성

### 클라이언트

- 화면: 메뉴 목록, 장바구니, 주문 확인, 주문 완료
- GitHub 저장소를 기준으로 버전 관리
- 환경변수로 Supabase URL과 공개용 키 관리
- 서버 전용 키는 클라이언트 코드에 포함하지 않음

### Supabase 서버

- PostgreSQL: 메뉴, 주문, 주문 상세 데이터 저장
- Auth: 관리자 기능이 필요할 경우 인증 적용
- Row Level Security(RLS): 테이블별 접근 권한 제한
- Edge Functions: 결제 연동이나 서버 전용 로직이 필요할 때 사용
- Storage: 메뉴 이미지 저장이 필요할 때 사용

### 서버 구현 계획

별도의 Node.js 서버를 운영하지 않고 Supabase를 백엔드 서버로 사용한다. GitHub Pages의 정적 클라이언트가 Supabase Publishable Key로 접근하고, 중요한 검증과 데이터 변경은 PostgreSQL 함수와 RLS 정책이 담당한다.

```text
GitHub Pages 클라이언트
        ↓ Publishable Key
Supabase
├── PostgreSQL: 카테고리·메뉴·옵션·주문·주문 상세
├── RPC: 주문 검증, 가격 재계산, 주문번호 발급
├── Auth: 운영자 로그인
├── RLS: 공개 사용자와 운영자 권한 분리
└── Realtime: 메뉴 및 주문 상태 실시간 갱신
```

### 4.1 피드백 기반 보완 계획

팀 피드백은 현재 코드와 대조해 아래처럼 반영한다. 이미 구현된 기능도 회귀 테스트를 추가해 다시 검증한다.

#### 현재 반영 상태

- [x] 서버가 `item_id`, 수량, 옵션 ID를 기준으로 가격과 합계를 다시 계산한다. 브라우저가 보낸 임의 단가는 신뢰하지 않는다.
- [x] 메뉴 화면에서 전체·커피·논커피·티·디저트 카테고리를 바로 볼 수 있다.
- [x] 기본 메뉴 별칭과 짧은 후속 응답 문맥을 일부 지원한다.
- [x] 추천 결과에 판매 중인 메뉴 카드와 가격을 함께 표시한다.
- [x] 가격 문의와 주문 의도를 분리하는 기본 로직이 있다.
- [x] 포장·매장 선택을 AI 주문 문맥에 반영한다.
- [ ] 사진 제공은 앞서 이미지를 제거하기로 한 현재 UI 결정에 따라 이번 범위에서 제외한다.
- [ ] StepUp English 피드백은 별도 프로젝트에 관한 내용이므로 카페 키오스크 범위에서 제외한다.

#### 1순위: 주문 정확성과 보안

1. **필수 옵션 확인 상태 도입**
   - 음료 주문 시 온도와 크기가 빠졌으면 즉시 장바구니에 넣지 않고 필요한 항목만 질문한다.
   - `pendingOrder`에 메뉴·수량·선택된 옵션·아직 필요한 옵션을 저장한다.
   - `M이요`, `둘 다`, `네`, `샷 추가` 같은 짧은 답변을 현재 주문 단계와 결합한다.
2. **다중 메뉴 주문 지원**
   - `아메리카노 1잔, 라테 1잔`을 여러 주문 항목 배열로 파싱한다.
   - 항목별 필수 옵션을 검증한 뒤 한 번에 장바구니에 반영한다.
   - 일부 항목만 불완전하면 완성된 항목을 잃지 않고 부족한 옵션만 추가 질문한다.
3. **수정·취소·수량 변경 강화**
   - `아아 두 잔 중 한 잔 취소`, `방금 그거 L로 변경`, `샷 추가 취소`를 직전 주문 항목에 적용한다.
   - 변경 직후 장바구니 수량과 코드 계산 금액을 응답에 사용한다.
4. **주문 완료 상태 도입**
   - `네, 주문할게요`를 확인 단계에서 결제/주문 확인 창으로 연결한다.
   - 완료·취소 후 `pendingOrder`를 정리해 무한 되묻기를 방지한다.
5. **서버 검증 회귀 테스트**
   - 조작 단가, 존재하지 않는 메뉴·옵션, 중복 옵션, 비정상 수량을 RPC가 거부하는지 자동 검증한다.

#### 2순위: 검색·추천·대화 문맥

1. **질의 유형별 검색 전략 분리**
   - 전체 메뉴·카테고리 목록 요청은 상위 5개 제한을 사용하지 않고 해당 범위 전체를 반환한다.
   - 추천·비교 요청에만 점수 기반 상위 결과 제한을 적용한다.
   - 특정 메뉴의 가격·옵션 질문은 해당 메뉴와 옵션을 반드시 검색 결과에 포함한다.
2. **판매 메뉴 안에서만 추천**
   - 판매하지 않는 음식은 추천 대상으로 만들지 않는다.
   - 식사 페어링 질문은 사용자가 말한 외부 음식과 어울리는 실제 판매 음료·디저트만 제안한다.
   - `커피 아닌`, `논커피`, `카페인 없는` 등 제외 조건을 먼저 적용한다.
3. **메뉴·옵션 별칭 사전 확장**
   - `아아`, `따아`, 오타 표현과 `중`, `M`, `톨`, `큰`, `L`, `그란데` 같은 크기 동의어를 정규화한다.
   - 부분 문자열만 우연히 겹치는 다른 메뉴는 대안으로 추천하지 않도록 최소 일치 기준을 둔다.
4. **대화 문맥 유지 강화**
   - 직전 사용자 문장뿐 아니라 `pendingOrder`, 최근 참조 메뉴 ID, 장바구니 항목을 검색 문맥에 포함한다.
   - 중간 옵션 질문에 답한 뒤 원래 주문 단계로 복귀한다.
   - 내부 검색 실패, 문서 번호, 기술적 사정은 고객 응답에 노출하지 않는다.
5. **응답 금액 단일화**
   - AI가 가격을 직접 추측하지 않고 메뉴 기본가와 옵션 추가금을 코드로 계산한 결과만 문장에 삽입한다.
   - 메뉴 카드, AI 답변, 장바구니, 주문 확인 화면의 금액이 같은 계산 함수를 사용한다.

#### 3순위: 정보 안전성과 사용성

1. **옵션 설명 데이터 보강**
   - 옵션에 설명과 추가 금액을 저장하고 `이 옵션은 뭐야?`에 해당 메뉴 기준으로 답한다.
2. **알레르기·식이 제한 안전 응답**
   - 메뉴 데이터에 원재료와 알레르기 정보를 추가하기 전에는 안전하다고 단정하지 않는다.
   - 정보가 없으면 확인 불가 사실과 직원 확인 필요성을 안내하고 주문 확정을 보류한다.
3. **검색 근거 표시 강화**
   - 근거 카드에 메뉴명뿐 아니라 설명, 기본 가격, 관련 옵션과 추가 금액을 함께 표시한다.
4. **요청 제한 대응**
   - 동일 요청 중복 전송 방지, 전송 버튼 잠금, 짧은 캐시와 재시도 간격을 적용한다.
   - 제한 발생 시 주문 상태를 잃지 않고 재시도 가능한 안내를 제공한다.
5. **로그 저장은 별도 승인 후 적용**
   - Supabase에는 세션 UUID, 이벤트 종류, 의도, 메뉴 ID, 주문 결과 같은 비식별 항목만 저장한다.
   - 이름과 질문·답변 원문은 저장하지 않으며, 운영자만 조회하도록 RLS를 적용한다.

#### 검증 계획

- 단위 테스트: 별칭·오타·부정 조건·가격/옵션 문의·다중 메뉴 파싱·짧은 후속 답변을 검증한다.
- 상태 테스트: 주문 시작 → 옵션 보완 → 수정/취소 → 확인 → 완료까지 장바구니와 `pendingOrder`를 검증한다.
- 서버 계약 테스트: 모든 가격이 Supabase RPC에서 재계산되고 조작 요청이 거절되는지 검증한다.
- 시나리오 테스트: 기존 41개 질문을 고정 회귀 세트로 정리하고 개선 전후 성공률과 실패 유형을 비교한다.
- 한·영 테스트: 동일 시나리오를 한국어와 영어로 실행하고 메뉴명·가격·장바구니 결과가 일치하는지 확인한다.
- 완료 기준: 필수 시나리오에서 허위 메뉴 추천, 금액 불일치, 처리했다고 말했지만 미반영되는 사례가 없어야 한다.

## 5. 권장 폴더 구조

```text
kiosk/
├── 구현계획.md
├── README.md
├── .env.example
├── index.html
├── styles.css
├── app.js

│   ├── migrations/
```

`dist/`는 `scripts/build-static.sh` 실행 시 생성되는 배포 결과물이므로 소스 저장소에는 보관하지 않는다.

## 6. 환경변수 초안

```dotenv
SUPABASE_URL=
SUPABASE_PUBLISHABLE_KEY=
```

실제 키가 들어간 `.env` 파일은 Git에 커밋하지 않는다. 저장소에는 변수명만 담은 `.env.example`을 둔다.

## 7. 보안 원칙

- `service_role` 키는 브라우저나 GitHub 저장소에 노출하지 않는다.
- 클라이언트가 직접 접근하는 테이블에는 반드시 RLS를 적용한다.
- 가격과 총금액은 클라이언트 입력만 신뢰하지 않고 서버에서 재검증한다.
- `request_id`를 고유하게 저장해 네트워크 재시도의 중복 주문을 방지한다.
- 비밀값은 로컬 환경변수 또는 배포 플랫폼의 Secret 기능으로 관리한다.

## 8. 완료 기준

- 사용자가 메뉴를 선택하고 주문을 생성할 수 있다.
- 생성된 주문과 주문 상세가 Supabase에 정상 저장된다.
- 주문 상태 변경이 클라이언트 화면에 반영된다.
- 권한 없는 사용자가 관리자 작업을 수행할 수 없다.
- 저장소에 비밀키가 포함되지 않는다.
- 핵심 주문 흐름에 대한 테스트가 통과한다.

## 9. 결정이 필요한 사항

- 운영자 계정과 관리자 화면의 최종 범위
- 실제 결제 기능 포함 여부
- 생성형 RAG를 위한 Edge Function 도입 여부
